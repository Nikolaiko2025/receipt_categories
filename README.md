# receipt_categories — веб-сервис (лабораторная работа 3)

Бэкенд приложения «Чеки»: веб-сервис (REST API) для SPA с итоговой бизнес-логикой
(кроме авторизации), работа с PostgreSQL через ORM (SQLAlchemy + asyncpg) и
хранение изображений/коротких видео услуг в MinIO.

* HTTP-документация (Swagger): <http://127.0.0.1:8000/docs>
* Интерфейс (страницы лаб. 1–2): <http://127.0.0.1:8000/receipt_categories_feed>

---

## 1. Запуск

```bash
docker compose up -d          # MinIO (9000/9001), PostgreSQL (5433), Adminer (8081)
pip install -r requirements.txt
python main.py                # http://127.0.0.1:8000
```

Переменные окружения — в `.env` (подключения к БД и к MinIO).

## 2. Единый формат ответа

Все методы домена «услуга» возвращают **один и тот же набор полей** — неважно,
это список, лента, черновик или ответ на публикацию/удаление:

| Поле | Тип | Описание |
|---|---|---|
| `id_receipt_category` | int | идентификатор (генерируется в БД, клиент не передаёт) |
| `title` | string | название услуги |
| `amount` | number \| null | сумма; `null`, если не заполнена |
| `description` | string \| null | описание |
| `image_url` | string | ссылка на изображение (файл лежит в MinIO) |
| `video_url` | string | ссылка на короткое видео (файл лежит в MinIO) |
| `date_created` | string \| null | дата создания (вычисляется на бэкенде) |
| `date_formed` | string \| null | дата публикации (вычисляется при публикации) |
| `date_completed` | string \| null | дата завершения (вычисляется при удалении; `null`, пока услуга не удалена) |
| `likes` | int | количество лайков |
| `is_creator` | 0 / 1 | `1` — услуга принадлежит текущему пользователю |
| `liked` | 0 / 1 | `1` — текущий пользователь поставил лайк |

Важно:

* **`status` в JSON не передаётся** — статус нужен только БД, в интерфейсе это разные окна;
* в JSON **нет сообщений об ошибках** и нет дублирования кода состояния:
  тело ошибки пустое (`{}`), код возвращает сам HTTP-ответ: `200`, `201`, `400`,
  `403`, `404`, `405`, `409`;
* системные поля (`id_receipt_category`, `status`, `creator`, `id_user`,
  `date_created`, `date_formed`, `date_completed`) **с клиента на изменение не
  принимаются**: создатель берётся из функции-синглтона, даты и статусы считает
  бизнес-логика;
* набор ключей JSON одинаков во всех ответах: **12 полей**, незаполненное
  значение — `null`, но ключ присутствует;
* поля `type`, `category`, `category_display`, `date` (дата операции) в сервисе
  **используются, но в JSON не отдаются**: данные лежат в БД, по ним работает
  фильтрация списка, а в ответ они не входят — клиент их не видит и не меняет.

Пример:

```json
{
  "id_receipt_category": 1,
  "title": "Оплата по дебиторке",
  "amount": 1200000.0,
  "description": "Оплата счёта по договору №45",
  "image_url": "http://localhost:9000/image/Оплата по дебиторке.jpg",
  "video_url": "http://localhost:9000/image/оплата_по_дебиторке.mp4",
  "date_created": "2026-09-15T10:00:00",
  "date_formed": "2026-09-15T10:00:00",
  "date_completed": null,
  "likes": 5,
  "is_creator": 0,
  "liked": 0
}
```

Ответ пользователя (`UserOut`): `{"id_user": 12, "username": "ivan"}`.

## 3. HTTP-методы веб-сервиса

Все адреса начинаются с `/api`.

### Домен «услуга»

| # | Метод | URL | Назначение | Параметры / тело | Ответ |
|---|---|---|---|---|---|
| 1 | `GET` | `/api/receipt_categories` | Список **опубликованных** услуг с фильтрацией на бэкенде | query: `type`, `category`, `title`, `min_amount`, `max_amount`, `date_from`, `date_to`, `expense`, `mine` | `200` — массив услуг |
| 2 | `GET` | `/api/receipt_categories/feed` | Лента **без указания ид**: первая опубликованная услуга (LIMIT 1) | — | `200` — услуга, `404` |
| 3 | `GET` | `/api/receipt_categories/feed/{id}` | Лента по ид; `?next=true` — **следующая** опубликованная услуга | path: `id`, query: `next` | `200` — услуга, `404` |
| 4 | `GET` | `/api/receipt_categories/draft` | Поля черновика: **ид не указывается**, запись не более 1 на пользователя | — | `200` — услуга, `404` |
| 5 | `POST` | `/api/receipt_categories` | **Добавление** услуги + загрузка изображения и короткого видео в MinIO | `multipart/form-data` | `201` — услуга, `400` (нет названия / кривая сумма или дата) |
| 6 | `PUT` | `/api/receipt_categories/publish` | **Публикация**: `Черновик → Опубликован` | JSON `PublishIn` (необязательно): `id_receipt_category`, `amount`, `date`, `description` | `200` — услуга, `404` |
| 7 | `DELETE` | `/api/receipt_categories/{id}` | **Удаление** (только soft delete: `status = Удален` + системная `date_completed`), только своих услуг | path: `id` | `200` — услуга, `403`, `404` |
| 8 | `POST` | `/api/receipt_categories/{id}/like` | Лайк от текущего пользователя: `1` — поставить, `0` — снять | JSON `{"value": 1}` или query `?value=0` | `200` — услуга, `404` |

**Фильтры метода 1** (сочетаются, отбор делает SQL-запрос через ORM, `WHERE`):

| Параметр | Пример | Что отбирает |
|---|---|---|
| `type` | `?type=income` | по типу операции |
| `category` | `?category=debit` | по коду категории |
| `title` | `?title=кредит` | частичный поиск по названию без учёта регистра |
| `min_amount`, `max_amount` | `?min_amount=1000000` | диапазон суммы |
| `date_from`, `date_to` | `?date_from=2026-09-01&date_to=2026-09-30` | диапазон даты операции |
| `expense` | `?expense=true` | `true` — только выплаты (`amount < 0`), `false` — только поступления |
| `mine` | `?mine=1` | `true` — только услуги текущего пользователя (по `id_user`) |

В списке всегда только опубликованные и **никогда не отдаются** записи в статусе `Удален`.
Поля `type`, `category`, `date` в ответ не входят (см. раздел 2), но фильтр по ним
работает: отбор идёт по данным в БД через ORM-запрос.

Лента по ид: `next=true` возвращает следующую опубликованную услугу после указанного
ида; если такой нет (конец ленты) — лента начинается сначала с первой опубликованной.
Записи в статусах `Черновик` и `Удален` по иду не отдаются (`404`).

**Поля формы метода 5 (`POST /api/receipt_categories`):**

| Поле формы | Обязательно | Назначение |
|---|---|---|
| `title` | да | название услуги (до 100 символов) |
| `type` | нет (по умолчанию `income`) | тип операции |
| `category` | нет (по умолчанию `debit`) | код категории |
| `category_display` | нет (по умолчанию `Дебиторка`) | название категории |
| `amount` | нет | сумма: `1200000`, `1 234,56` |
| `date` | нет | дата: `ГГГГ-ММ-ДД` или `ДД.ММ.ГГГГ` |
| `description` | нет | описание |
| `image` | нет | **файл** изображения (а не URL) |
| `video` | нет | **файл** короткого видео (а не URL) |

Поля `type`, `category`, `category_display`, `date` сохраняются в БД (в них есть
данные, по ним работает фильтрация), но **в ответ не возвращаются** — они скрыты
от клиента. Если их не передать — берутся значения по умолчанию из таблицы выше.

Ответ содержит созданный черновик (`status` = `Черновик`, `creator` = текущий
пользователь, `date_created` = момент обращения). Если черновик у пользователя
уже есть — обновляется он (на пользователя не бывает более одного черновика).

### Домен «пользователь»

| # | Метод | URL | Назначение | Тело | Ответ |
|---|---|---|---|---|---|
| 9 | `POST` | `/api/users/register` | Регистрация нового пользователя | JSON: `username` (1–50), `password` (1–255) | `201` — `UserOut`, `409` (имя занято), `400` (нет/пустые поля) |
| 10 | `POST` | `/api/users/login` | Аутентификация — **заглушка для лаб. 4** (без токенов) | JSON: `username`, `password` | `200` — `UserOut`, `404` (нет пользователя), `403` (неверный пароль), `400` |

### Какие переходы статусов разрешены

Статус живёт только в БД и меняется лишь этими методами:

| Откуда | Куда | Метод |
|---|---|---|
| (новая запись) | `Черновик` | `POST /api/receipt_categories` |
| `Черновик` | `Опубликован` | `PUT /api/receipt_categories/publish` |
| `Черновик` / `Опубликован` | `Удален` | `DELETE /api/receipt_categories/{id}` |

Обратного перехода в черновик нет: повторная публикация и публикация чужой/удалённой
записи возвращают `404`, удаление чужой услуги — `403`.

### Примеры запросов (Postman / Insomnia)

```text
1.  GET    /api/receipt_categories?type=income&min_amount=500000
2.  POST   /api/receipt_categories                 (form-data: title, image, video)
3.  GET    /api/receipt_categories/draft
4.  PUT    /api/receipt_categories/publish         (JSON {}, ид не нужен)
5.  GET    /api/receipt_categories/feed
6.  GET    /api/receipt_categories/feed/1?next=true
7.  POST   /api/receipt_categories/1/like          (JSON {"value": 1})
8.  DELETE /api/receipt_categories/2
9.  POST   /api/users/register                     (JSON {"username": "ivan", "password": "qwerty123"})
10. POST   /api/users/login
```

### Коды ответов и краевые случаи

Тело ответа-ошибки **пустое (`{}`)**: только код состояния — без сообщений и
без дублирования кода в JSON (код состояния и есть результат):

| Что отправить | Код | Почему |
|---|---|---|
| `GET /api/receipt_categories/99` (и `-1`, `999999999999`, `abc`) | `405` | такого метода в API нет: услуга по иду отдаётся только через ленту |
| `GET /api/users/11` | `404` | метод не зарегистрирован (домен пользователя — только `register`/`login`) |
| `GET /api/receipt_categories/feed/99?next=true` | `404` | исходной услуги не существует |
| `GET /api/receipt_categories?min_amount=abc` | `400` | сумма не является числом |
| `GET /api/receipt_categories?date_from=01.01.2026` | `400` | в фильтре дата только `ГГГГ-ММ-ДД` |
| `POST /api/receipt_categories` без `title` / `title="   "` | `400` | нет названия, запись **не создаётся** |
| `POST /api/receipt_categories` `amount="не число"` или `date="вчера"` | `400` | данные не разобраны, запись **не создаётся** (до загрузки файлов) |
| `POST .../{id}/like` `{"value": 5}` или `{"value": "раз"}` | `400` | допустимы только `0` и `1` |
| `PUT .../publish` повторно | `404` | черновика больше нет |
| `PUT .../publish` `{"id_receipt_category": 1}` | `404` | это не черновик текущего пользователя |
| `DELETE /api/receipt_categories/99` / `-1` | `404` | такой услуги нет |
| `DELETE /api/receipt_categories/999999999999` | `404` | ид вне диапазона колонки `integer` (защита от 500) |
| `DELETE /api/receipt_categories/abc` | `400` | ид не является числом |
| `DELETE /api/receipt_categories/1` | `403` | услуга принадлежит другому пользователю |
| `DELETE /api/receipt_categories/7` | `404` | уже удалена |
| `POST /api/users/register` с существующим именем | `409` | имя занято |
| `POST /api/users/login` неверный пароль / нет пользователя | `403` / `404` | аутентификация |
| `PUT /api/receipt_categories/feed` | `405` | метод не поддерживается роутом |
| `GET /api/nonexistent` | `404` | маршрута нет |

Все ошибки разбора запроса (несуществующий маршрут параметра, нечисловые
фильтры, неполное JSON-тело) обрабатывает единый обработчик
`RequestValidationError` в `main.py` и возвращает `400 Bad Request`.

Успешные коды: `200` — получение/изменение, `201` — создание услуги или
пользователя. Консистентность: `201`/`200` возвращаются только после
`commit` в БД, а `400`/`403`/`404`/`409` означают, что база не изменилась.

| Настройка | Значение |

| endpoint | `localhost:9000` (консоль — `localhost:9001`) |

`06a76531dab841d093900af5286bcb0d.jpg`. В поля `image_url` / `video_url` таблицы
сохраняется **имя файла**, сам файл лежит в MinIO (`core/storage.py`).
Клиенту отдаётся собранный URL; старые записи (полный URL или путь `/static/...`)
отдаются без изменений.

## 5. Таблицы БД

### `receipt_categories` — услуги

| Поле | Тип | Ограничения | Описание |
|---|---|---|---|
| `id_receipt_category` | `integer` | PK | идентификатор, генерируется БД |
| `title` | `varchar(100)` | NOT NULL | название услуги |
| `type` | `varchar(20)` | NOT NULL | `income` / `expense` |
| `category` | `varchar(20)` | NOT NULL | код категории: `debit`, `sales`, `credit`, `salary`, `suppliers` |
| `category_display` | `varchar(50)` | NOT NULL | название категории для интерфейса |
| `amount` | `numeric(15,2)` | | сумма операции |
| `date` | `date` | | дата операции |
| `description` | `text` | | описание |
| `status` | `varchar(11)` | NOT NULL | `Черновик` / `Опубликован` / `Удален` — **только в БД, в JSON не отдаётся** |
| `image_url` | `varchar(255)` | NOT NULL | имя файла изображения в MinIO |
| `video_url` | `varchar(255)` | NOT NULL | имя файла видео в MinIO |
| `date_created` | `timestamp` | NOT NULL | дата создания (вычисляется на бэкенде) |
| `creator` | `varchar(50)` | NOT NULL | создатель (из функции-синглтона, не с клиента) |
| `date_formed` | `timestamp` | | дата публикации (вычисляется при публикации) |
| `id_user` | `integer` | NOT NULL, **FK → `users.id_user`** | создатель (идентификатор пользователя) |
| `date_completed` | `timestamp` | | дата завершения (вычисляется при удалении) |

Связи: `receipt_categories.id_user` → `users.id_user` (многие услуги — один
пользователь); `receipt_categories.id_receipt_category` ←
`likes.id_receipt_category` (многие лайки, без FK в таблице `likes`).

### `users` — пользователи

| Поле | Тип | Ограничения | Описание |
|---|---|---|---|
| `id_user` | `integer` | PK | идентификатор |
| `username` | `varchar(50)` | NOT NULL | логин (уникальность проверяется методом регистрации) |
| `password` | `varchar(255)` | NOT NULL | пароль (хеширование — лаб. 4) |

В демо-данных есть пользователь `import` (id `12`): на него заведены записи,
полученные импортом (`creator = 'import'`), — у каждой услуги есть реальный
`id_user` с внешним ключом.

### `likes` — лайки (связь «пользователь ↔ услуга»)

| Поле | Тип | Ограничения | Описание |
|---|---|---|---|
| `id_user` | `integer` | PK, **без FK** | кто поставил лайк (отношение: многие `likes` → один `users`) |
| `id_receipt_category` | `integer` | PK, **без FK** | что лайкнули (многие `likes` → один `receipt_categories`) |
| `id_like` | `integer` | PK, **без FK** | идентификатор лайка, генерируется БД (`nextval('likes_id_like_seq')`) |

Первичный ключ — все три колонки. Внешних ключей в таблице нет: связи
«пользователь → лайки» и «услуга → лайки» описаны только отношением в модели ORM
(`models/receipt_categories.py`). Повторный лайк той же пары не даёт
бизнес-логика метода: перед вставкой проверяется, есть ли уже такой лайк.

### Объекты MinIO

| Поле | Значение |
|---|---|
| бакет | `image` |
| объект | файл изображения/видео, имя — латинское `<uuid>.<расширение>` |
| тип содержимого | `image/jpeg`, `image/png`, `video/mp4` и т. п. |

## 6. Текущий пользователь (функция-синглтон)

Авторизация делается в 4-й лабораторной, поэтому во **всех** методах пользователь
зафиксирован константой и возвращается функцией-синглтоном
(`core/current_user.py`):

```python
CURRENT_USER_LOGIN = "test_user"          # константа
_current_user: User | None = None         # кэш: создаётся один раз

async def get_current_user(db: AsyncSession) -> User:
    ...
```

Функция используется как зависимость FastAPI в каждом методе
(`user: User = Depends(current_user)`): методы списка, ленты, черновика,
добавления, публикации, удаления, лайка — все берут создателя оттуда.
Отсюда же берётся `id_user` для лайков.

## 7. Структура проекта (по методичке)

| Слой | Файл | Что делает |
|---|---|---|
| **Handler** (п. 1.8) | `api/rest.py` | разбор HTTP-запроса, валидация (`400`), бизнес-правила статусов, вызов Repository |
| **Repository** (п. 1.7) | `db/repository.py` | все ORM-запросы к PostgreSQL: список с фильтрами, лента, черновик, сохранение, лайки, пользователи |
| **Сериализаторы** (п. 1.6) | `api/serializers.py` | `ReceiptOut`, `UserIn`, `UserOut`, `PublishIn` |
| **Модели / схема** (п. 1.4) | `models/*.py` | `Receipt_categories`, `User`, `Like` — структура совпадает с таблицами БД (сверено) |
| **Синглтон пользователя** | `core/current_user.py` | `get_current_user()` — константа `test_user` во всех методах API |
| **Хранилище файлов** (раздел 2) | `core/storage.py` | MinIO: генерация латинских имён, загрузка, сборка URL |
| **Страницы** (лаб. 1–2) | `api/handlers.py`, `templates/` | серверный интерфейс, те же таблицы и та же бизнес-логика |
| **Настройки** | `core/config.py`, `.env` | подключение к PostgreSQL и MinIO |

Зависимости: домены (`api/rest.py` → `db/repository.py`) → **модели**
(`models/*.py`) → **таблицы БД**; **страницы** (`templates/*` → `api/handlers.py`)
→ те же домены и модели.

## 8. Страницы интерфейса (серверные, лаб. 1–2)

| URL | Назначение |
|---|---|
| `/` | корень сайта — редирект на ленту (`303`) |
| `/receipt_categories_feed`, `/receipt_categories_feed/{id}?next=true` | лента услуг (по одной, LIMIT 1) |
| `/receipt_categories_add` | добавление: создание черновика и публикация |
| `/receipt_categories_grid` | плитка опубликованных услуг с фильтром по сумме |
| `/receipt_categories_grid/{id}/delete` | логическое удаление (`status = Удален`) |

Страницы используют те же таблицы и ту же бизнес-логику, что и веб-сервис;
статусы и системные поля не выводятся в шаблоны как данные пользователя.

## 9. Проверка

Основной сценарий (10 запросов: список с фильтром, добавление с картинкой и видео,
поля черновика, публикация, лента без ид, лента по ид `?next=true`, лайк, удаление,
регистрация, вход/выход) выполняется в Postman/Insomnia по адресам из раздела 3;
документация с готовыми схемами — на странице `/docs`.

Дополнительно проверено:

* краевые случаи из методички: `id = -1`, `id = 999999999999`, `id = ""`,
  `id = "abc"` — сервер **не отвечает 5xx**, тело ответа всегда JSON;
* все коды ответов: `200`, `201`, `400`, `403`, `404`, `405`, `409` (больше двух);
* структура БД сверена с моделями ORM: 3 таблицы ↔ 3 модели, лишних и
  недостающих полей нет;
* консистентность ответа и БД: `200`/`201` — только после `commit`,
  `400`/`403`/`404`/`409` — база не изменилась (например, кривая сумма
  не создаёт черновик, файлы в MinIO в этом случае не загружаются);
* MinIO: файлы из формы попадают в бакет `image` под латинскими именами,
  в БД сохраняются именно имена файлов.
